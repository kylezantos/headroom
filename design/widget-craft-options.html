Two evidence caveats that shape everything below

  • The -ios61- / -ios67- renders carry macOS type metrics. The harness is a macOS binary, so SwiftUI text styles resolved as macOS sizes. Those PNGs prove iPhone geometry and margins, not iPhone type. Every iOS point size in this report is from Apple’s HIG text-style table (iOS: title3 20 / headline 17 / subheadline 15 / footnote 13 / caption 12 / caption2 11; macOS: title3 15 / headline 13 / subheadline 11 / footnote 10 / caption 10 / caption2 10). Every crop cut from one is badged iPhone geometry, macOS type.
  • The full/noSpend/claudeOnly/… fixtures print “· Resets in 3h” on every row because DemoScreenshotData.window(...) stamps every window resetsAt: now + 3h. Only the states and settingsPreview fixtures show varied reset copy. Not a widget bug.

How to read these

Verification key. Every area header carries the report’s badge for the claim it rests on.

✔ code  the cited lines were re-read ✔ px  the render was sampled ▲ computed  arithmetic from the HIG table — wants a Simulator or device capture before anyone builds on it

Panels. Render crop panels are cuts from the 2× ImageRenderer PNGs, embedded at 1 CSS px = 1 pt unless the note says otherwise; those renders were appearance-verified, so their colour is trustworthy. iPhone geometry, macOS type marks the ones cut from an ios render. Mock panels are HTML drawn at 1 px = 1 pt from the resolved tokens and the point sizes each area names — the system font stack, no webfonts, no images.

Ruled overlays are drawn in app points over the crop. Where this page re-sampled a gap and got a different number from the report, the panel note says both.

Family verdicts
  • Small — closest in composition and the only calm family, but the furthest from the popover in truth: it prints a stale or retired window at full ink and full colour.
  • Medium — a good idea (two providers, one comparison axis) at the wrong scale: a numeral larger than the popover’s own in a column half a popover card’s width, which is why the countdown was dropped.
  • Large — has all the popover’s content and none of its rhythm: a repeated tooltip sentence on every row, two hairlines, a numeral that steps four times by density, and ~40 % of the tile spent on gaps that are all the same size.

F · Foundations

Six areas. F1 and F2 are prerequisites for most of the rest — the type scale and the reserved numeral column. F5 is the structural move that makes every other fix land on both platforms at once.

M · Meters, colour, truth

Eight areas. Four HIGHs about what the bar is allowed to say: healthy paints neutral, critical is one treatment, stale recedes, and the small family stops printing values the continuity policy has retired.

L · Layout and rhythm

Eight areas. The large tile spends ~40 % of its height on gaps that are all the same size; the medium tile’s tightest pairing in the product is its label→bar; the small tile centres its rows in a void. L8 is folded into L1 and listed there for the record.

W · Writing and states

Nine areas. The large family prints a tooltip four times, the wire label instead of the display label, three footer forms, and two copy sets for the same five conditions.

Not a craft pass

Bigger than this round

Listed, not decided — no controls. These are the pieces of work the areas above lean on or defer to.

  1. WidgetTypeScale + @ScaledMetric plumbing at ~30 call sites (F1) — no schema bump, but the keystone; wants characterization tests. Land first or everything is tuned twice.
  2. Fill-aware density selection (L1-B) — Core arithmetic; changes LargeWidgetDensity’s initializer.
  3. CoreText port of capHeightCentered / OpticalLeading (L6) — shared code that must be safe in a widget extension’s process.
  4. Moving HeadroomLargeWidgetView into the shared module (F5) — file moves between targets; both extensions built; gallery smoke on both platforms.
  5. A dual-platform render harness (or an iOS Simulator snapshot target) — without it, F1-class regressions are structurally invisible; every iOS type claim here is ▲.
  6. A verified .vibrant / .accented / StandBy pass on hardware (M7, M8).
  7. Envelope schema bumps, none recommended this round — percentage mode (“used”), MeterStyle, AccountTitleInk, typed capability state (would let M5’s glyph become a word), multi-account rows.
  8. One status-state model across the two extensions (W4) — a Core enum + both timeline providers.
  9. Interactive widgets (AppIntent buttons) — every status card ends with “open Headroom” because the widget cannot act.
