## 1. Sync contract: iCloud KVS is eventually consistent, unfenced, and silently lossy

**Sources**: `docs/plans/2026-07-04-002-feat-ios-companion-widget-icloud-plan.md`; `docs/release/release-operations.md` (Track B); `docs/release/website-dmg-release.md` lines 171-188 and 305-330; `BUGS.md` "iPhone sync" (415-436) and "Sign-in handoff residuals" (199-218); `docs/plans/2026-07-07-003-ios-widget-stale-sync-investigation.md`; `docs/plans/2026-07-08-004-widget-card-parity-handoff.md`; `docs/plans/2026-09-19-2217-feat-per-account-polling-schedule-plan.md` (KTD9, R19, AE7); `docs/plans/2026-08-02-001-feat-widget-two-provider-cap-cleanup-plan.md` (R6, R9, KTD5); `docs/plans/2026-07-15-001-feat-ios-demo-review-readiness-plan.md` (R3); code `Sources/HeadroomCore/Sync/{SyncedWidgetSnapshotModels,iCloudSnapshotSync,IOSWidgetTimelineMapping}.swift`, `UsageStore.swift:1082-1103`.

Rules the plan must carry:

1. **KVS has no writer fence, so the data-version rollout is a skew matrix, not a switch.** Release ops states it twice: "an older iCloud writer can overwrite v3 because iCloud KVS provides no writer fence" and downgrade "is not a rollback path." The plan needs a table of {old, new phone} x {old, new Mac} x {one Mac, two Macs}. Today's rule is newest-valid-wins by `generatedAt`, ties local (`SyncedWidgetSnapshotResolution.newestValid`, `IOSWidgetSnapshotState.resolve`). With two keys the new phone must read both and define how a newer v3 from an un-updated second Mac competes with an older v4 (it would silently drop the extra accounts). Decide and test this, do not leave it to the default.
2. **Old phones must keep reading exactly the bytes they read today, under today's key.** The decode gate is exact-equality on the sync envelope version (`header.schemaVersion == SyncedWidgetSnapshotEnvelope.schemaVersion`, currently 1) plus `WidgetSnapshotEnvelope.supports` (1...3). Anything new at the old key, even a sync-envelope bump, lands old phones on "Update Needed" (`IOSWidgetSnapshotState.incompatibleSchema`, which short-circuits even when the other source has valid content). This confirms the settled "new key + keep publishing v3" and means the v3 publish must keep its own fresh `generatedAt` on every export, not be a stale copy.
3. **Top-level provider fields stay "the primary account" forever** (INVENTORY D10, and the 2026-07-20 plan). The iOS widgets and cache-hydrated widget path can then keep rendering the primary without touching the four widget styles.
4. **The KVS write path cannot report failure today.** `UbiquitousKeyValueSyncStore.set` always returns `true`, and `iCloudSnapshotPublisher.export` is `try? sync.publish(...)`. A quota violation (bigger multi-account payload) is invisible. The plan's "quota observation" must be built on the `didChangeExternallyNotification` quota-violation reason and surfaced in the `--dump-phone-sync` diagnostic and the phone's Settings diagnostics (origin: `IOSWidgetContentOrigin`). Evidence it matters: the Jul 2026 "iPhone shows stale data" incident was a silent publish failure.
5. **Every preference that changes what the phone draws needs an export trigger and a test for it.** `setWidgetPrioritySource` forgot `exportPhoneSyncSnapshot()` (BUGS.md 410-413), even though the 2026-08-02 plan's R6/R9 required "survives the sync round-trip." The tests covered projection, not the trigger. U2-C ("Same as Mac" meter style, percentage mode, title ink) adds three more setters of exactly this class (`UsageStore.swift:457-472` do not export today). Rule: one test per setter asserting an export fires, plus fix the `setWidgetPrioritySource` bug in this round.
6. **Per-account polling KTD9 and R19 must be amended, not worked around.** KTD9 deliberately made extras' merges not export ("Extras' merges do not export... bounding exposure to the app-group container read that BUGS.md records as a main-thread block"). All-accounts-on-phone reverses the first half. BUGS.md 199-208 says that main-thread block already got worse when export moved to per-primary-merge. So "coalesced publishes" is not optional polish: debounce, and move the app-group container read and the JSON encode off the main actor in the same change. Update AE7 and the `UsageStoreTests` that pin "extras do not export."
7. **A KVS request key (U5-B) must be nonce-gated and age-gated on the Mac.** KVS values persist; the Mac would see the last request on every launch. This is my inference from KVS semantics, not a repo-recorded failure: carry a request id and timestamp, keep a last-handled id, ignore stale requests. Treat a remote request as a user-initiated front-of-queue refresh (per the polling doc, user work bypasses the duty-cycle gate but its time still counts) and coalesce, because at the 20-account envelope a "full user refresh drains everything back to back by design" (about 100 s of Claude probes). Receipts must be honest about latency, which is unverified (hence the planned spike).
8. **Demo mode may not write KVS.** Demo plan R3: demo "never fetches providers, publishes to iCloud, overwrites the real App Group snapshot cache." A pull-to-refresh request key is an iCloud write; in demo, pull-to-refresh must be local-only (no request key, no CloudKit subscription registration). `--demo` stays a non-persistent override.
9. **Verification of sync needs a provisioned Mac build.** `swift run` and default `build-app.sh` builds have no KVS entitlement (`build-app.sh` strips it; with it but no profile, macOS SIGKILLs at launch, exit 137). End-to-end evidence needs `HEADROOM_ENABLE_ICLOUD_ENTITLEMENT=1` plus both profiles (host and widget, separately), a signed bundle, and a physical iPhone. Extend `--dump-phone-sync` (run from the signed bundle only) to print both keys, byte counts, publishedAt/generatedAt and the quota flag, categories only, no payload. Unit tests use the in-memory `iCloudKeyValueSyncing` double.
10. **When a phone surface looks wrong, check data before rendering.** The stale-sync and widget-parity handoffs each burned days tuning tokens while the real cause was data (`Updated 20 hrs ago`, missing Mac entitlement). Sequence the plan's QA: confirm `publishedAt` and origin first, then tokens. WidgetKit also caches by kind and build: a changed render may need a build-number bump or reinstall, and 30+ stale registered app copies once confused QA (clean up before widget checks).
11. **Track B applies.** `docs/release/release-operations.md` requires a separate signed-candidate matrix for "a reset-accuracy or widget snapshot schema change" across macOS popover, macOS widgets, iPhone companion, and iOS widgets, with v1/v2/v3 migrations, a future-schema fixture that stays untouched and shows incompatible, and "equal-generation local data wins." A new sync data version triggers it. Keep each surface's result separate.
12. **Surface skew honestly.** New phone with old Mac (v3 only) should look like a single-account phone, not "broken" and not claim accounts are missing. Mac 1.4.1 is public and iOS is already stamped 1.5 (`project.yml`); the Mac that publishes v4 is not out yet.

## 2. Multi-account on the phone reverses four earlier "primary-only" decisions

**Sources**: `docs/plans/2026-07-20-001-fix-provider-setup-multi-account-release-stabilization-plan.md` (lines 126, 143-144: "Do not add iOS account management. iPhone and widgets continue to receive only the primary"; "Compact surfaces remain primary-only"); `docs/release/ios-app-review-testflight.md` step 10; `UsageStore.swift:1087-1089` comment ("the widget schema and the iPhone mirror stay single-account"); `docs/plans/2026-07-03-002-feat-multi-account-profiles-plan.md`; AGENTS.md "Multi-account (Jul 2026)"; `docs/solutions/logic-errors/claude-partial-usage-window-freshness.md`.

Rules:

1. **The TestFlight acceptance runbook contradicts the new feature and will fail the release gate.** Step 10 requires "add, fail, rename, and remove an additional Mac account; confirm the iPhone app and widgets remain byte-for-byte focused on each provider's built-in account and never show the extra account label or setup state." Rewrite it as a multi-account acceptance (stack order, Make Main, stale/needs-sign-in per account, account removal) and keep the "no provider credential action exists on iOS" check (step 11). Rewrite the Review Notes too (they say the demo exposes "Claude and Codex").
2. **Widgets stay primary-only.** Widget craft plan and styles plan both hold "envelope schema stays at 3" and "multi-account widget rows" as not built, by decision; styles plan stop-condition says stop if a widget envelope schema bump is needed. Keep the widget path reading the primary projection from the new payload. Do not smuggle accounts into widget recipes.
3. **Provenance is per window and per account, not per card.** `claude-partial-usage-window-freshness.md`: model provenance at the narrowest independently refreshed unit; never advance an observation time unless the source returned it; bump the serialized schema when old consumers could read new freshness states as live. The slim account-window type in the new payload must still carry per-window `freshness`/`observedAt`, and the phone's oldest-live "Updated" stamp must come from window `observedAt`, never from `generatedAt` or `publishedAt`.
4. **Render what the envelope carries; never infer rows.** `docs/solutions/codex-window-kind-mislabel.md` (window identity from the self-describing field, no synthesized rows; a `prolite` plan legitimately has only Weekly) and AGENTS.md Cursor rule (never render `Included` beside named pools; incomplete layouts fail stale). Window order normalization (5-hour first) must be one shared Core function (`UsageSnapshot.fiveHourFirst()` exists), not a phone-side re-sort: the Sep 2026 specimen drifted because it rendered a raw fixture (BUGS.md 663-673).
5. **Privacy line stays: no email, no config path, no same-login signal in the payload.** AGENTS.md says the same-login badge is metadata only and detection-only; account titles must be the Mac-resolved, de-duplicated titles. Update the Mac copy "Sends only your usage numbers through iCloud" (`WidgetSettingsSection.swift:76`) once titles sync, and `docs/release/privacy-policy.md` ("provider names, percentages remaining, reset times, and freshness timestamps").
6. **Capacity and parity.** Tested envelope is 20 per provider (`AccountRegistry.testedEnvelope`); Cursor is single-account by design. The phone must be exercised at `--demo multi-20` equivalent, with a "N more on your Mac" fallback only if a cap is adopted, and the parity rule (AGENTS.md) means all four providers, every account; say so explicitly where the phone cannot do something.
7. **Row keys.** Motion plan RI1: key meter rows by window kind plus occurrence, never by position, so one row arriving does not roll its neighbour's value. Same for account stacking keyed by account id, and the "arrival registry keyed by account so a rebuilt row does not re-run its draw-in" (BUGS.md 608-616). A new snapshot arriving must not replay the entrance.

## 3. Shared UI across Mac and iOS: the build plumbing has already broken twice

**Sources**: `BUGS.md` 366-373 (hand-picked Core file lists), `docs/release/1.1-release-evidence.md` lines 59-61 (it broke again: `ProviderSetup.swift` missing from both iOS targets), `docs/plans/2026-10-02-1247-feat-widget-styles-plan.md` U1/KTD11 and "Build traps", `project.yml` lines 90-150, `BUGS.md` 578-584 (L9P), `DESIGN.md` rules 1-2 and component table, `docs/plans/2026-09-04-004-feat-ios-companion-mirror-ui-plan.md` ("accept small constant duplication for now"; shared UI module deferred), `.context/ios-parity/INVENTORY.md` headline 2.

Rules:

1. **The iOS targets still enumerate `Sources/HeadroomCore/Models/*.swift` one file at a time** (`project.yml` 99-110, 142-150). Every new Core file the shared UI needs is a silent iOS break (it has happened on 2026-09-09, 2026-09-23, and 2026-07-20). Make "iOS targets take the whole `Models` folder" the first unit, put an iOS simulator build (`xcodebuild -scheme HeadroomIOS` and `HeadroomIOSWidgets`, `generic/platform=iOS Simulator`) in every unit's verification and the pre-PR check, and treat `project.yml` as the authority, regenerate `Headroom.xcodeproj` with xcodegen (the committed pbxproj is generated; hand edits drift). `WidgetSnapshotProjector.swift` is deliberately excluded from the iOS targets, so an envelope-to-`UsageWindow` adapter (INVENTORY D12) must live in an included file.

The same applies to a new shared folder: prefix and check collisions with SwiftUI/UIKit/WidgetKit names. Known AppKit leaks to resolve with `#if canImport` or CoreText twins (the widget typography twins already exist): `NSFont` percent-column measuring in `UsageBarView.swift:144-147`, `OpticalLeading.swift`, `HeadroomMotion` (`NSApp.currentEvent`, `CAMediaTimingFunction`).

After the move, delete the phone's private copies (`HeadroomTheme`, `UsageBarView` in `HeadroomIOS`, `lowChip`) instead of leaving two. DESIGN.md "Known gaps" says iOS motion values are kept in step by hand; the shared folder retires that gap, so update the table.
4. **The Mac popover must be re-accepted live after the move.** AGENTS.md: meter visual acceptance must use the live `MenuBarExtra` window; `--render-popover` is a sanity check only. A refactor of `MeterGauge`/`ProviderStyle` touches pixels on the Mac. Budget one live Mac pass in both appearances (ask first, per the no-screen-takeover rule), and run `--render-popover` for the Settings swatches.
5. **Offscreen renders cannot validate phone layout.** `docs/solutions/popover-scrollview-zero-height.md`: `ImageRenderer` proposes a concrete size, so a zero-height ScrollView bug rendered perfectly offscreen and in 228 green tests. Widget craft/styles plans add: `ImageRenderer` ignores `.dynamicTypeSize` and uses macOS type metrics, and the harness is macOS-only (BUGS.md 739-745). So the phone's Dynamic Type multiplier (U1-B), iPad masonry (U8-A) and 6.1" metrics need headless `xcrun simctl` screenshots at specific content-size categories (the widget craft plan's verification step 5 used "`xcrun simctl`, headless, no visible Simulator window"). Add xxLarge and the AX sizes to the matrix.
6. **L9P becomes closable.** BUGS.md 578-584: the Mac's Widgets & iPhone preview strip has no iPhone tile "if the iOS tile ever lands in a shared, platform-neutral library." With the shared folder it can; decide explicitly (in or out) rather than leaving the BUGS entry dangling.
7. **Mac app-target tests will not run while any Headroom.app is open** (BUGS.md 7-14, the single-instance guard also runs in the XCTest host), and test runs leak UserDefaults suites (BUGS.md 42-47). New app-target tests for the shared UI should use temp or in-memory defaults, and the verification step must close other Headroom copies first (never `killall`).
8. **`Scripts/capture-demo-screenshots.sh` line 113 runs `killall Headroom`**, which kills Kyle's live menu bar app (BUGS.md 404-409) and violates the release-ops rule against broad process termination. Fix it (terminate only the worktree build's PID) before using it for App Store screenshots; until then use `HEADROOM_IOS_ONLY=1`.
9. **Setup/problem copy is test-pinned.** `Tests/HeadroomCoreTests/ProviderSetupOutcomeTests.swift` (R2C6, 146-180, 376-390): one sign-in verb ("Sign In", "Sign In Again"), no "connect", curly apostrophes, a non-breaking space before every em dash, no borrowed button labels ("Check Again", "Refresh") in phase copy. The settled "typed 'on your Mac' problem lines" must be a Core enum fed from `ProviderSetupOutcome`/`FailureReason`, added to those test sets (the way `WidgetStatusCopy` + `WidgetStatusCopyTests` did for widgets), never hand strings in views. The phone never shows a CLI command or a credential action (mirror-ui plan R6, TestFlight step 11). Known stale copy to fix: `IOSCompanionView.swift:96` and `docs/release/appstore-listing.md` say "Sync snapshot to iPhone"; the Mac switch is "Sync usage to iPhone" (`WidgetSettingsSection.swift:75`, `WidgetStatusCopy.swift:52`).
10. **Swatches/grids.** Styles plan KTD13: an `HStack` of fixed thumbnails crashed AppKit layout, so the Mac picker uses a `LazyVGrid`; build the iOS swatch rows as a grid too. The Appearance specimen must be inert (no arrival, no accessibility announcements): the Mac specimen reuses `announcesAccessibilityEvents` as its gate (BUGS.md 609-611); give the shared specimen an explicit `stagesArrival`-style input.

## 4. SwiftUI layout and motion: decisions Kyle already made that the phone will re-trigger

**Sources**: `docs/solutions/popover-scrollview-zero-height.md`; `docs/solutions/ui/swiftui-layout-owned-drag-position.md`; `docs/solutions/ui/spend-identity-row-width-budget.md`; `docs/plans/2026-09-04-002-feat-subtle-motion-system-plan.md` (S2A, M1A, M2A, M4A, M7A, M9C, AR1, AR2, NB1, RI1); `BUGS.md` 608-630; AGENTS.md "Reduce Motion and accessibility are best-effort"; `DESIGN.md` rules 4 and 6; global CLAUDE.md Motion rule.

Rules:

1. **Entrance motion (U7-B) has history.** M9C (superseded 2026-09-06): Kyle reviewed a popover entrance live and "called for instant: no entrance motion at all, not even on the first open." The Mac keeps only the first-open meter arrival (AR1: fill draws in, 350 ms delay, own spring). U7-B is settled for the phone, but the constraints below are not negotiable carry-overs:
   - **AR2: never roll a numeral up from "0%"**; it reads as a false "0% left." Numerals paint their real value on frame one; only the fill and the card's rise animate.
   - **M4A: no layout shift, no count-up through intermediate values**, one `numericText(value:)` transition inside the already-fixed numeral column; arrival fires on `.pending to .live` only, later updates are M1A (one critically damped `valueSpring` for fill, roll, and severity colour).
   - **M2A: the minute tick** ("Updated N min ago", every "Resets in") rolls on the minute value; waiting clocks do not (WC1).
   - **S2A Reduce Motion**: anything that travels, scales, blurs, resizes or rolls digits becomes instant; opacity crossfades keep their timing. Per AGENTS.md this is best-effort and low priority, not a blocker.
   - **No pulsing/looping attention animations, ever** (DESIGN.md rule 6; global CLAUDE.md).
   - Motion tokens come from the shared tokens, never ad hoc curves in a view.
2. **The dot-matrix spinner must be bound to real progress.** `ProviderCardIdentityRows.swift:683`: "real-progress spinner (bound to the retry cycle, not decorative)"; `ClaudeSetupViews.swift:195-198`: a code-review finding removed a spinner that "would wait forever" when no process existed. The phone's "Waiting for Mac" state has no completion signal of its own. Use the spinner only while a re-read or a Mac refresh request is actually in flight (with the receipt), and give the idle waiting state a still vessel. Otherwise it becomes a looping attention animation on a state that may last days.
3. **Container height and content change share one animation scope.** M7A (Kyle: "container contraction after a removal was jerky... must share one animation scope") and NB1 (neighbours follow a resized card). This applies directly to iPad masonry reflow when an account stack grows or the banked-reset capsule opens, and to the phone's stacked accounts.
4. **If masonry is a custom `Layout`, it owns placement; no `.offset` handovers.** `swiftui-layout-owned-drag-position.md`: four attempts failed by splitting position between `Layout` placement and `.offset`; never use `DispatchQueue.main.async`/`Task.yield` to get a frame boundary between two state changes; keep a card that changes form one persistent view (no `if/else` branch swaps mid-motion, since an inserted view gets no "from" geometry); commit to the model after the animation. The doc's own related-issues note says the sibling trap is scroll views with no useful ideal height.
5. **Scroll/size containers.** `popover-scrollview-zero-height.md`: a `ScrollView` has no ideal height; inside any self-sizing container (sheet detents, a popover, a fitted section) it collapses to zero unless a measured height is pinned (`onGeometryChange`). The phone's Settings sheet (S1-A) and any iPad popover must be checked in a real simulator window, not offscreen. iPad is not `UIRequiresFullScreen` and supports all four orientations (`Sources/HeadroomIOS/Info.plist`, enforced by `Scripts/verify-ios-release.sh`), so Split View and Slide Over give compact widths: drive masonry column count from measured width, not only `horizontalSizeClass` (current `MirrorView.swift` uses the size class).
6. **U1-B (scale popover proportions about 1.15x) collides with rows that carry almost no slack, by arithmetic from repo constants.** `spend-identity-row-width-budget.md` (2026-09-08): the spend identity row is 299 pt wide and the title is its only flexible element, so a 6 pt capsule change made "Anthropic API" truncate. R2C8 (2026-09-09) later freed some room by measuring the widest total instead of reserving "$0,000.00" (BUGS.md 678-681, "re-check a 'Last 30 days' chip on the next shoot"), so the exact slack today is unmeasured, but the principle stands: every capsule, type, or inset change is a width change. Scaling 299 pt by 1.15 needs about 344 pt of content width. A 6.1" iPhone (393 pt) with today's phone insets (screen 18 + tile 17, so about 323 pt) is short by roughly 6%, and a 375 pt device by about 11%. These figures are computed from constants, not measured. Rule: measure row widths with UIKit/CoreText (the doc says width sums beat screenshots), at the largest Dynamic Type size, and plan to flex insets or let the card width define the scale rather than a fixed 1.15x of the card; the Mac measures the percent column with `NSFont`, so the shared amount-column measurement needs a platform twin.
7. **Colour meaning.** DESIGN.md rule 4: severity colours mean usage level only; account/lifecycle states use neutral ink; red is for a provider refusal. The phone's amber account-state notice and "Low" chip are existing drift (BUGS.md 682-685 for the chip); the shared rows should retire them by construction.

## 5. Widgets: what the parity round must not undo, and what is still unverified

**Sources**: `docs/plans/2026-09-11-001-feat-widget-craft-plan.md`; `docs/plans/2026-10-02-1247-feat-widget-styles-plan.md`; `docs/qa/2026-10-03-widget-config-upgrade-spike.md` and `-widget-styles-acceptance.md` (result tables are empty); `BUGS.md` 719-778; `Sources/HeadroomIOSWidgets/HeadroomIOSWidgets.swift`; `docs/plans/2026-07-08-004-widget-card-parity-handoff.md`.

Rules:

1. **Keep the widget kind strings.** Both extensions deliberately keep their original kind (`HeadroomIOSUnifiedUsageWidget`) so placed widgets survive; the Static to `AppIntentConfiguration` upgrade is **unverified on device** and developers report frozen placeholders (BUGS.md 756-759). The spike checklist has no recorded result. Since the parity release is the first time public iPhone users (App Store 1.0 from Jul 26) cross that conversion, the plan must either get the spike result first or write the release-note fallback ("remove and re-add the widget") into the release unit. Lock Screen accessory families and a Control Center control are a second, separately untested kind/family addition on the same widget; treat them as a new spike item, not as covered by KTD1. Also keep `.contentMarginsDisabled()`, `.disfavoredLocations([.iPhoneWidgetsOnMac], …)` (consistent with "Mac availability off"), and no `recommendations()`.
2. **Old-data dimming has no threshold to reuse and the obvious ones are wrong.** BUGS.md 763-765 and the styles plan "Deferred" list: when the Mac sleeps the envelope stays "live" and an iPhone widget shows hours-old numbers in full colour; "new behavior for every style, with no existing threshold." Derive it, do not invent a constant: the polling doc's numbers are the evidence (per-account failure backoff `chosen x 2^n` capped at `max(30 min, effective)`, never-signed-in extras at 4x, effective interval stretches under the duty-cycle gate at high account counts). Primary exports follow each primary merge, so `generatedAt` advances at the primary's cadence including backoff. A fixed 15 or 30 minute threshold would dim a healthy 20-account Mac. Make it a pure Core recipe applied by every style (KTD3), tested with the polling constants, and consider carrying the chosen interval additively (INVENTORY G12).
3. **Widget numbers/state recipes are pure Core under `swift test`; views are verified only by renders.** `HeadroomWidgetSharedUI` view code is verified by the `--render-widgets` sweep, not tests (BUGS.md 746-751). New phone-facing widget logic (dimming, accessory-family selection, shed ladders) goes into `WidgetStyleRecipe`-style Core types.
4. **The render sweep has known blind spots that bear on App Store shots.** It is macOS-only; does not pose the iPhone DEMO capsule's 14 pt top inset (BUGS.md 777-778), so App Store screenshot mode can overflow small tiles while the sweep stays green; and `.accented`/vibrant/StandBy rendering and Liquid Level's wash are "reasoned, not measured" (BUGS.md 724-731, 760-762). Any widget in a marketing frame needs a real simulator capture at 6.1" and 6.9", and the Lock Screen widgets inherit the tinted/vibrant risk (never draw an opaque full-bleed fill; styles plan KTD9).
5. **The WCF7 overflow rule is binding for any new widget or phone element**: nothing overlaps or clips; drop whole elements, then truncate text; never `minimumScaleFactor`; numerals, bars, marks never shrink; new payload views carry `.headroomWidgetProbe()`; read rendering mode through `@HeadroomWidgetRendering`, never `widgetRenderingMode` directly (AGENTS.md Gotchas).
6. **Phone widget status copy lives in `WidgetStatusCopy` (Core)** with tests; add new states there (the settled "waiting screen" and the multi-key states).
